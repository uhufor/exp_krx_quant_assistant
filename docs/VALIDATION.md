# OOS / 워크포워드 검증

백테스트 성과가 **미래에도 재현될 숫자인지, 과거에 맞춰 깎은 결과인지**를 가릅니다.

| 관련 문서 | 내용 |
|---|---|
| [백테스트](BACKTEST.md) | 검증의 기반이 되는 단일 구간 실행 |
| [전략 정의](STRATEGY.md) | 스윕 대상이 되는 팩터·규칙·임계값 |
| [포트폴리오](PORTFOLIO.md) | `portfolio.*` 스윕 대상 정책 |

---

## 왜 필요한가

전 구간 백테스트는 숫자를 하나 줍니다. 그런데 파라미터를 손으로 몇 번 바꿔 좋은 값을 고르는
순간 **그 전 구간이 사실상 인샘플**이 되고, 리포트는 그 사실을 표시하지 않습니다. 이동평균
창을 20에서 60까지 훑어 가장 수익이 높은 값을 고른 뒤 "총수익 80%"라고 적으면, 그 80%는
성과가 아니라 **탐색 결과**입니다.

검증은 구간을 학습(IS)과 검증(OOS)으로 나눠 이 둘을 분리합니다.

```
holdout      [────────── 학습 ──────────][── 검증 ──]

walkforward  [── 학습 ──][검증]
             [───── 학습 ─────][검증]                 (anchored, 확장창)
             [─────── 학습 ───────][검증]

             [── 학습 ──][검증]
                  [── 학습 ──][검증]                  (rolling, 고정 길이)
                       [── 학습 ──][검증]
```

폴드마다 **학습 구간에서만** 파라미터를 고르고, **검증 구간에서 그 파라미터의 성과**를
잽니다. 학습 구간과 검증 구간은 하루도 겹치지 않습니다.

## 실행

### `validation-run`

```bash
uv run python -m quant_krx validation-run STRATEGY_ID [옵션들]
```

| 인자/옵션 | 의미 | 기본값 |
|---|---|---|
| `strategy_id` (필수) | 검증할 전략 id | — |
| `--spec` | 검증 스펙 JSON 파일 경로 또는 `-`(stdin). **파라미터 그리드는 여기에만 넣습니다** | 없음 |
| `--mode` | `holdout`(단일 분할) \| `walkforward` | `walkforward` |
| `--folds` | 워크포워드 폴드 수(`holdout`이면 무시) | `3` |
| `--test-ratio` | 전체 구간 중 검증에 쓸 뒤쪽 비율 | `0.3` |
| `--anchored` / `--rolling` | 학습창 확장 vs 고정 길이 롤링 | `--anchored` |
| `--objective` | 학습 구간 선택 기준: `sharpe` \| `total_return` \| `calmar` | `sharpe` |
| `--symbols` `--start` `--end` `--fees` `--slippage` `--data-source` `--benchmark` | `strategy-backtest`와 동일 규약 | 동일 |

CLI 옵션은 스펙 파일 위에 덮어씁니다 — 그리드는 파일에 고정해 두고 폴드 수만 바꿔가며
돌리는 흐름을 위한 것입니다.

```bash
# 파라미터 스윕 없이 IS/OOS 성과만 비교
uv run python -m quant_krx validation-run my_strategy \
  --mode holdout --data-source fixture --start 2024-01-02 --end 2024-12-18

# 워크포워드 4폴드, 롤링창
uv run python -m quant_krx validation-run my_strategy --folds 4 --rolling

# 실제 KRX 10년치(오프라인) — 롤링창의 효과를 보려면 이 정도 길이가 필요합니다
uv run python -m quant_krx validation-run my_strategy \
  --data-source fixture_10y --start 2015-01-02 --end 2024-12-30 --folds 3
```

### `validation-list` / `validation-show`

```bash
uv run python -m quant_krx validation-list
uv run python -m quant_krx validation-list --strategy-id my_strategy --limit 50
uv run python -m quant_krx validation-show 20260729-1a2b3c4d
```

## 파라미터 그리드

스펙 파일의 `grid`에 넣습니다. 키는 **무엇을 바꿀지 가리키는 주소**이고 값은 시도할
후보 목록입니다.

```json
{
  "mode": "walkforward",
  "n_folds": 3,
  "objective": "sharpe",
  "grid": {
    "portfolio.max_positions": [3, 5, 10],
    "factor.sma@5.window": [3, 5, 8],
    "rule.per_rule.threshold": [10, 15, 20]
  }
}
```

```bash
uv run python -m quant_krx validation-run my_strategy --spec spec.json
```

### 주소 문법

| 키 | 대상 | 예 |
|---|---|---|
| `portfolio.<필드>` | 포트폴리오 정책(`max_positions` · `rebalance` · `sizing` · `initial_cash`) | `portfolio.max_positions` |
| `factor.<팩터id>.<파라미터>` | 그 팩터가 **참조되는 모든 곳**의 파라미터 | `factor.momentum.window` |
| `factor.<팩터id>@<현재값>.<파라미터>` | 파라미터가 현재 그 값인 참조만 | `factor.sma@5.window` |
| `rule.<룰id>.threshold` | 단일 Predicate 룰의 상수 임계값 | `rule.per_rule.threshold` |

**`@<현재값>` 선택자가 왜 필요한가.** 골든크로스처럼 같은 팩터를 서로 다른 파라미터로 두 번
쓰는 전략이 흔합니다. `sma(5) > sma(20)` 전략에서 선택자 없이 `factor.sma.window`를 스윕하면
단기·장기 창이 **같은 값이 되어 신호가 영영 발생하지 않습니다**(조용히 성과 0). 단기 창만
바꾸려면 `factor.sma@5.window`를 씁니다.

**팩터 파라미터는 정의뿐 아니라 규칙·공식 안까지 전부 바뀝니다.** 실행 시 실제로 쓰이는
파라미터는 `factor_refs`가 아니라 Rule/Formula 피연산자와 `portfolio.ranking`에 적힌 값이기
때문입니다. `factor_refs`만 바꾸면 저장은 되는데 계산은 그대로인 **조용한 무효 스윕**이
됩니다.

### 제약

- **저장된 정의는 변경되지 않습니다.** 파생 정의와 리졸버 래퍼를 메모리에서만 만듭니다.
- **임계값 스윕은 단일 Predicate 룰만** 가능합니다. AND/OR로 결합된 룰은 "어느 상수인가"가
  모호하므로 조용히 첫 번째를 고르지 않고 **거부**합니다 — 스윕 대상 조건은 별도 룰로
  분리하십시오.
- **주소 오타·적용 불가는 폴드를 돌리기 전에 즉시 실패**합니다(미존재 룰, 미지의 키, 임계값을
  특정할 수 없는 복합 룰). 조합 단위 격리에만 맡기면 같은 실패가 조합 수만큼 반복된 뒤
  "모든 폴드 실패" 메시지에 원인이 파묻힙니다.
- **어느 조합도 거래를 내지 못하면** 그 사실을 짚어 줍니다 — 가장 흔한 원인이 위의 선택자
  누락이기 때문입니다.
- 조합 수는 곱으로 늘어납니다(3 × 3 × 3 = 27조합 × 3폴드 = 학습 81회 + 검증 3회).

## 결과 읽기

```
┌─────────────────┬──────────────┐
│ 항목            │ 값           │
├─────────────────┼──────────────┤
│ 방식            │ walkforward · 확장창 │
│ 폴드            │ 3/3 성공     │
│ 학습(IS) sharpe │ 1.842        │
│ 검증(OOS) sharpe│ 0.412        │
│ 성과 저하율     │ 77.63%       │
│ 파라미터 안정성 │ 33.33%       │
│ OOS 일관성      │ 33.33%       │
│ OOS 합성 수익률 │ -4.20%       │
│ OOS 합성 MDD    │ 18.90%       │
└─────────────────┴──────────────┘
⚠️  검증 구간에서 sharpe가 78% 떨어졌습니다 — 과최적화 가능성이 높습니다
⚠️  폴드마다 다른 파라미터가 선택되었습니다 — 노이즈에 맞춰졌을 수 있습니다
```

| 지표 | 의미 | 나쁜 신호 |
|---|---|---|
| **성과 저하율** | `1 - OOS/IS`. 인샘플 대비 얼마나 무너지는가 | 50% 초과 |
| **파라미터 안정성** | 폴드 간 같은 파라미터가 선택된 비율 | 50% 미만 |
| **OOS 일관성** | 검증 구간이 수익인 폴드 비율 | 50% 미만 |
| **OOS 합성 수익률/MDD** | 각 폴드 검증 구간만 이어붙인 곡선의 성과 | — |

**OOS 합성 곡선**은 폴드마다 자기 자본에서 다시 시작하므로 그냥 이으면 계단이 생깁니다.
폴드 내부 수익률만 가져와 곱으로 이어붙여 "이 전략을 계속 굴렸다면 겪었을 성과"를 만듭니다.

읽을 때 주의할 점:

- **학습 구간 성과가 0 이하면 저하율은 표시되지 않습니다**(`N/A`). 부호가 뒤집혀 엉뚱한
  값이 되기 때문이며, 애초에 학습 구간에서도 실패한 전략입니다.
- **그리드가 없으면 파라미터 안정성은 항상 100%**입니다. 고를 것이 없으면 흔들릴 것도
  없습니다.
- **`calmar`는 낙폭이 0이면 선택 대상에서 제외**됩니다. 무한대가 승자가 되면 "거의 거래하지
  않는 파라미터"가 항상 뽑히기 때문입니다.
- **저하율이 100%를 넘으면** 검증 구간에서 부호가 뒤집혔다는 뜻입니다(학습 +, 검증 −).
  "100% 이상 나빠질 수 없다"가 아니라 `1 - OOS/IS`의 산식상 자연스러운 값입니다.

## 확장창과 롤링창

`--anchored`(기본)와 `--rolling`은 **학습 구간의 시작점**만 다릅니다. 검증 구간은 동일합니다.

```
확장창 (--anchored)                        롤링창 (--rolling)
폴드1 학습 2015-01-02~2021-12-30           폴드1 학습 2015-01-02~2021-12-30
폴드2 학습 2015-01-02~2022-12-30           폴드2 학습 2016-01-02~2022-12-30
폴드3 학습 2015-01-02~2023-12-30           폴드3 학습 2017-01-01~2023-12-30
      ↑ 시작 고정, 데이터가 계속 쌓임             ↑ 길이 고정, 통째로 뒤로 밀림
      "모든 과거를 기억한다"                      "오래된 국면은 잊는다"
```

| | 확장창 | 롤링창 |
|---|---|---|
| 가정 | 과거는 많을수록 좋다 | 오래된 과거는 지금과 다르다 |
| 강점 | 표본이 많아 추정이 안정적 | 폴드 간 조건이 공평, 최근 국면에 민감 |
| 약점 | 폴드마다 학습량이 달라 비교가 불공정 | 표본이 적어 지표가 요동칠 수 있음 |

**동시에 쓸 수는 없지만(배타적 선택), 두 번 돌려 대조하는 것 자체가 진단입니다.**

| 확장창 | 롤링창 | 해석 |
|---|---|---|
| 좋음 | 좋음 | 가장 믿을 만함 — 데이터 양·최근성에 의존하지 않음 |
| 좋음 | 나쁨 | **옛 데이터가 성과를 떠받치고 있음** — 최근 시장에선 안 통할 수 있음 |
| 나쁨 | 좋음 | 시장 성격이 바뀌었고 전략은 새 국면에 맞음 |
| 나쁨 | 나쁨 | 창 방식 문제가 아님 — 전략 자체를 다시 볼 것 |

기본은 확장창입니다(데이터를 버리지 않고, 실제 운용과 더 비슷함). 학습 구간에 성격이 명백히
다른 국면(2020 코로나 폭락, 2022 금리 급변)이 들어 있을 때 롤링으로 반증해 보십시오.

두 가지 주의:

- **짧은 구간에서는 비교가 의미를 잃습니다.** 폴드 수를 늘리면 `fixture`(1년치)에서도 숫자는
  갈리지만, 그때 학습창은 몇 달로 쪼그라들어 거래가 몇 건 나오지 않습니다 — 두 방식의 차이가
  아니라 표본 부족을 보는 셈입니다. **학습창이 최소 수년은 되도록** 기간과 폴드 수를 잡으십시오
  (`--data-source fixture_10y`로 10년 × 5폴드면 학습창이 5년입니다).
- **롤링창 길이는 따로 지정할 수 없습니다.** `학습창 = 전체 기간 × (1 - test_ratio)`로
  파생됩니다. "학습 2년 고정 + 검증 1개월씩" 같은 조합은 현재 표현할 수 없고,
  `--start`/`--end`로 전체 기간을 조절해 우회합니다.

## 백테스트 이력과의 관계

검증 1회는 내부적으로 (그리드 조합 × 폴드)만큼 백테스트를 돌립니다. 그 중간 실행은
**`backtest_runs`에 기록하지 않습니다** — 사용자가 의도적으로 돌린 백테스트 이력이
검증 부산물에 파묻히지 않게 하기 위함입니다. 검증 1회는 `validation_runs`에 1행으로
요약됩니다.

백테스트와 달리 **캐시가 없습니다.** 검증은 비싸고 명시적으로 돌리는 작업이라 조용한
캐시 히트가 오히려 혼란스럽기 때문입니다.

비용 면에서 중요한 사실 하나: 데이터는 전 구간을 **한 번만** 조립하고 폴드는 날짜로만
자릅니다. 팩터는 전 구간에서 계산된 뒤 잘린 인덱스로 정렬되므로 **폴드를 잘라도 워밍업
손실이 없습니다** — 첫 폴드라고 해서 이동평균이 비어 있지 않습니다.

## GUI

[백테스트] 탭 하단의 **OOS / 워크포워드 검증** 패널에서 실행합니다. 대상 종목·기간·
데이터소스는 위쪽 백테스트 폼의 값을 그대로 물려받으므로, 백테스트를 돌려본 뒤 같은
설정으로 바로 검증할 수 있습니다. 파라미터 그리드는 JSON으로 입력하고, 결과는 요약 표 ·
OOS 합성 자산곡선 · 폴드별 표로 표시됩니다. 하단 이력 행을 클릭하면 과거 검증을 다시
불러옵니다.
