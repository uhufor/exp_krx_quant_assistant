## 현재 플랫폼의 구조적 공백 (근거)

1. **백테스트가 종목별 독립 실행**이다. `workspace/backtest.py::run_single_symbol_backtest`가
   종목마다 따로 vectorbt를 돌리고 `BacktestReport.per_symbol`로 합산한다 — 즉 모든 종목이
   각각 자본 100%를 쓴다는 가정이며, 계좌 관점의 성과가 존재하지 않는다.
2. **스크리닝 결과가 전략으로 흐르지 않는다.** `strategy/definition.py::Universe`는 정적 심볼
   리스트뿐이고(`jobs/daily.py:180` `defn.universe.symbols or watchlist`), 스크리닝 실행 결과는
   휘발성(EPIC-03 D5)이라 전달 경로 자체가 없다. R04로 팩터 랭킹 스크리닝은 되는데 그 결과를
   백테스트에 태울 수 없는 것이 현재 최대 단절이다.
3. **백테스트 결과가 저장되지 않는다.** `strategy_runs`는 데일리 전용이고, `strategy-backtest`
   CLI와 GUI 백테스트 결과는 어디에도 영속되지 않는다. 전략 여러 개를 비교하는 것이 플랫폼의
   존재 이유인데 직전 실행과 비교할 방법이 없고, 전종목+DART 백테스트는 비용이 크다.

## P3 — 백테스트 실행 이력 영속 + 결과 비교 (**구현 완료, 2026-07-27**)

**해결한 문제**: 공백 3.

**사용자 확정 결정**: ① 캐시 키에 데이터 커버리지 지문 포함 ② 실행 시 항상 자동 저장
③ 저장 범위 = 메트릭 + 자산곡선(거래내역 미저장).

**구현 결과**
- `storage/backtest_schema.py::backtest_runs`(additive 신설) + `storage/db.py` CRUD 4종.
- `workspace/fingerprint.py` — 정의 지문(전이 폐포, `_collect_bundle` 재사용) · 파라미터 지문 ·
  커버리지 지문의 3축 합성 캐시 키.
- `workspace/persistence.py` — `BacktestReport` ↔ 저장 행 변환. 복원 리포트는 `from_cache=True`.
- `workspace/serialization.py` — 직렬화 계약 단일화(원래 `api/schemas/backtest.py`에 있던
  함수를 내리고 API가 재export). 저장 결과와 GUI 응답이 같은 포맷임을 구조적으로 보장.
- `WorkspaceService.backtest(..., use_cache=True)` — 캐시 조회 → 미스 시 실행 → 자동 기록.
- CLI: `backtest-list` / `backtest-show` / `backtest-compare` + `strategy-backtest --no-cache`.
- API: `POST /api/backtests`(`use_cache`, 응답에 `run_id`/`from_cache`) ·
  `GET /api/backtests/runs` · `GET /api/backtests/runs/{run_id}`.
- GUI: `BacktestHistoryPanel` — 이력 목록 + 체크박스 2건 이상 선택 시 비교 표와 자산곡선 오버레이.
- 테스트 46건 신규(841 → 887 통과). 지문 단위 테스트가 "과거 값 정정" 같은 요약 통계로는
  못 잡는 변화까지 커버.

**설계상 중요한 귀결(후속 작업 시 전제)**
- **커버리지 지문은 DB 쿼리가 아니라 조립된 `FactorInput` 전체 해시로 계산한다.** OHLCV는
  DuckDB를 거치지 않고 `DataProvider`에서 직접 조립되므로(`build_factor_input`) DB만 보면
  OHLCV 변화를 놓친다.
- 그래서 **캐시 조회는 데이터 준비 이후**에 일어나고, 절감되는 비용은 팩터 계산 + vectorbt
  실행분이다. 데이터 수집 호출 자체의 절감은 R04 커버리지 바이패스가 담당한다. 수집 전에
  캐시를 조회하도록 "최적화"하면 새 데이터가 영원히 반영되지 않으므로 하지 말 것.
- 캐시 히트 리포트의 `results[*].trades`는 항상 비어 있다(거래내역 미저장). CLI/GUI 모두
  이를 사용자에게 명시하고 `--no-cache` 경로를 안내한다.

**비영향 범위**: `factors/`, `screening/`, 데일리 파이프라인 무변경(확인 완료).

## P1 — 포트폴리오 백테스트 (**구현 완료, 2026-07-27**)

**해결한 문제**: 공백 1. 실전 적용의 최대 갭.

**사용자 확정 결정**: ① 후보 초과 시 **공식/팩터 값 기준 랭킹**(미지정 시 종목코드 오름차순)
② **균등 분배만**(사이징은 열거형으로 두어 후속 확장) ③ **거래는 리밸런싱 시점에만**.

**구현 결과**
- `StrategyDefinition.portfolio`(`PortfolioPolicy` + `RankingSpec`, `schema_version` 1→2 additive).
  부재 시 기존 종목별 경로 그대로.
- `workspace/portfolio.py`(순수, vectorbt 미import) — 보유 의도 상태 → 리밸런싱일 상위 N 선택 →
  목표 비중 행렬.
- `workspace/backtest.py::run_portfolio_backtest` — `from_orders(size_type='targetpercent',
  group_by=True, cash_sharing=True, call_seq='auto')`.
- 참조 무결성 3곳 배선(아래 "핵심 교훈" 참고), CLI/GUI/API/P3 이력 전부 연동.
- 테스트 69건 신규(886 → 955 통과).

**핵심 설계 판단(후속 작업 전제)**
- **`from_signals`가 아니라 `from_orders` + 목표 비중**이다. 신호는 종목마다 독립적이고 자본을
  모르므로 "최대 N종목"을 표현할 수 없다. 비중을 직접 계산해 넘기면 자본 공유·보유 수 제한·
  리밸런싱이 한 번에 표현되고 결정론도 유지된다.
- **`per_symbol`은 포트폴리오 모드에서 비어 있다.** 자본을 공유하면 종목별 독립 성과가
  정의되지 않는다. GUI/CLI는 계좌 전체 지표로 폴백한다.
- **새 참조 슬롯을 추가하면 세 곳을 함께 고쳐야 한다**: `strategy/validation.py`(factor_refs 일치
  검사 — 빠뜨리면 랭킹 팩터가 "잉여"로 저장 거부됨), `workspace/service.py::_transitive_closure`
  (활성 참조 보호·Export 번들), `workspace/evaluation.py::_required_data_by_kind`(데이터 계약 —
  빠뜨리면 밸류에이션을 안 받아와 전 종목이 NaN으로 조용히 탈락).
- **스키마에 컬럼을 더할 때는 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 마이그레이션 목록에
  넣어야 한다.** `_ensure_schema`가 "테이블이 다 있으면 DDL 스킵"이라 `CREATE TABLE`만 고치면
  기존 DB에 영영 반영되지 않는다.

**후속 여지(v1에서 의도적으로 제외)**
- 역변동성 등 추가 사이징(열거형에 additive).
- 부분 청산/추가 매수, 리밸런싱 주기 외 손절.
- 종목별 기여도 분해(포트폴리오 모드에서 `per_symbol`을 의미 있게 채우려면 별도 정의 필요).

## P2 — 스크리닝 → 전략 유니버스 동적 연결 (**구현 완료, 2026-07-28**)

**해결한 문제**: 공백 2.

**사용자 확정 결정**: ① 유니버스는 **리밸런싱마다 재평가** ② 동적 유니버스는 **portfolio 필수**
③ **as-of별 결과 캐시**로 반복 비용 절감.

**구현 결과**
- `Universe.kind = "static" | "screening"`(whitelist fail-closed, kind 미기재는 static으로 하위호환).
- `workspace/dynamic_universe.py` — 앵커 계획 + backward 매칭(아래 "핵심 교훈").
- `data/screening_cache_schema.py::screening_result_cache` + `ScreeningService.resolve_symbols`.
- `DataProvider.list_symbols(market, as_of=None)` 확장 — 생존 편향 방지.
- CLI/API가 `UniverseResolver`를 주입(workspace ↔ screening 형제 관계 유지), GUI 유니버스 편집기.
- 테스트 44건 신규(955 → 999 통과).

**핵심 교훈(후속 작업 전제)**
- **닭-달걀 문제**: 백테스트는 대상 종목의 OHLCV를 미리 수집해야 하는데 종목은 리밸런싱마다
  정해진다. 해법은 실행 계층이 **달력 앵커**로 미리 스크리닝해 합집합을 수집 대상으로 삼고,
  엔진이 **실제 거래일**로 물으면 그 이하 최근 앵커 결과를 **backward 매칭**해 주는 것.
  매칭을 빼면 수집 대상과 실제 후보가 어긋나 "왜 안 담겼는지 알 수 없는" 결과가 된다.
- **생존 편향은 기본값이 함정이었다**: `list_symbols`가 `date.today()`를 하드코딩하고 있었다.
  pykrx는 `get_market_ticker_list(date)`로 시점별 조회를 지원하므로 프로토콜에 `as_of`를
  additive로 넣어 해결했다. **ETF/ETN 필터는 여전히 현재 기준**(pykrx 미지원) — 남은 한계.
- **D5 완화**: EPIC-03은 "실행 결과 미저장"이었으나 반복 백테스트 비용 때문에 캐시를 도입했다.
  이력 테이블이 아니라 캐시이며(조건 해시로 자동 무효화, 조건 삭제 시 동반 삭제), 2순위
  D1(스크리닝 델타 알림)이 필요로 하는 스냅샷과는 **성격이 다르다**(그쪽은 이력이 필요).

**남은 한계**
- ~~ETF/ETN 제외 필터의 시점 미반영~~ — **해소(2026-07-28)**. `DataProvider.list_etf_symbols`/
  `list_etn_symbols`(as_of 지원)로 provider 경유로 바꿨다. 원래는 시점 문제로만 기록했으나
  실제로는 **데이터소스 자체를 무시**하는 더 넓은 결함이었다 — `--data-source fixture`로
  오프라인 실행해도 이 필터가 켜져 있으면 pykrx가 로드되어 KRX 로그인을 시도했고,
  자격증명이 없으면 `IndexError`로 스크리닝이 죽었다.

  (2026-07-28)**. 아래 "실데이터 검증 결과" 참고.
- 앵커는 달력 기준이라 리밸런싱일과 며칠 어긋날 수 있다(backward 매칭으로 정합성은 보장).
